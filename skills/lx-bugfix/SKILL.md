# lx Bugfix：先复现，再修复

当用户描述的是已有功能出错、回归、报错、性能退化、测试失败或线上异常时，走本 Skill；当用户要增加一个以前不存在的能力时，走 `/lx-grill`。

## 目标

把“修一下这个 Bug”转换成可复现、可验证、可回滚的修复任务。核心产物不是一段猜测性的修改，而是：

```text
现象 → 最小复现 → 根因证据 → 回归测试 → 最小修复 → 验证证据
```

## 第 0.5 步：选择修复模式

先给本次任务标记一个 `bugfix_mode`，再决定流程深度：

### `fast`：快速修复

仅当以下条件全部满足时使用：

- 复现步骤稳定，期望结果已经确认；
- 根因已由代码、测试或日志直接定位；
- 改动集中在一个小范围，通常是一个函数、组件或配置；
- 存在稳定的公共测试切面，能快速写出回归验证；
- 不涉及竞态、跨模块契约、权限、数据迁移、支付、发布或不可逆操作。

路径：

```text
复现 → 一条回归测试 → 用户确认轻量计划 → 最小修复 → 相关验证
```

快速模式跳过 `/lx-brainstorm` 和 `/lx-subagent`，但不跳过复现、回归测试、计划确认和验证。

### `standard`：标准修复

适用于根因已基本明确，但涉及多个文件、状态迁移、接口联调、UI 行为或需要相邻回归的 Bug。

路径：

```text
复现 → 根因证据 → 回归测试计划 → 用户确认 → lx-tdd → 相邻回归
```

### `deep`：深度修复

适用于竞态、性能退化、跨模块影响、数据/权限风险、线上回归、根因不明或存在多个修复方向的 Bug。

路径：

```text
复现与观测 → 根因定位 → lx-brainstorm → 完整计划确认 → lx-tdd/lx-subagent → 全量相关验证
```

遇到任一升级条件就从 `fast` 升为 `standard`，从 `standard` 升为 `deep`；不为了追求速度而压低验证等级。

## 第 0 步：先判定是不是 Bug

先读取项目的 `docs/lx-workflow/CONTEXT.md` 和相关 ADR（如果存在），再把请求归类：

- **Bug 修复**：已有行为与已确认的预期不一致，或出现错误、回归、性能退化、数据丢失、竞态等问题。
- **新需求**：用户希望系统新增以前不存在的能力或改变已确认的产品规则，转到 `/lx-grill`。
- **混合请求**：先拆成 Bug 修复和新需求两条线，不把新规则藏在修复里。

如果预期行为本身尚未确认，先记录为待确认项；不要把产品决策伪装成技术修复。

## 第 1 步：固定复现事实

收集并写入 Bug 修复计划或本地问题记录：

- 实际表现与期望表现；
- 最小复现步骤、输入数据和触发条件；
- 发生环境、版本、提交或接口上下文；
- 错误信息、日志、截图或失败测试输出；
- 影响范围和是否存在回归版本；
- 可观察的公共测试切面（seam）。

先运行项目已有的最小复现命令。无法复现时，保留“未复现”的状态，继续收集证据或向用户询问缺失事实，不得直接声称已修复。

## 第 2 步：定位根因

从复现入口向下追踪调用、数据和状态变化，区分：

- 触发条件：什么操作让问题出现；
- 直接原因：哪条逻辑产生了错误结果；
- 根因：为什么现有约束没有阻止错误；
- 非目标：哪些相邻问题不在本次修复范围。

如果只有现象没有证据，先补诊断，不要先改最可能的文件。若存在多个合理修复方向，再使用 `/lx-brainstorm` 比较取舍；简单且根因已确认的 Bug 可以跳过方案发散。

## 第 3 步：写 Bug 修复计划

使用 `/lx-writing-plan` 或等价的本地计划，计划必须包含：

```yaml
plan_status: awaiting-user-confirmation
```

计划至少包括：

1. `bugfix_mode`、Bug 现象、期望结果和最小复现；
2. 根因证据与未决假设；
3. 回归测试切面和 Red 失败条件；
4. 最小修复任务、依赖、非目标和回滚方式；
5. 相关验证命令、手工验收和剩余风险。

计划应优先围绕一个可观察行为拆分任务。例如：

```markdown
1. 为旧响应覆盖新响应建立失败回归测试
   - 测试切面：列表查询结果应用入口
   - 验收：旧请求晚返回时不覆盖最后一次查询结果

2. 增加查询序号守卫的最小实现
   - 阻塞：任务 1
   - 验收：相关回归测试通过，不改变正常单次查询结果

3. 运行相邻回归验证和手工验收
   - 阻塞：任务 2
```

`fast` 模式的计划可以很短，但必须保留模式、复现、回归测试、最小修复、验证命令和非目标；“这是小问题”不能替代这些事实。

## 第 4 步：计划确认门

只有用户明确确认计划后，才允许进入代码阶段：

```text
我确认这个 Bug 修复计划，可以进入实现阶段。
```

确认前可以继续补充证据、调整计划和询问未决事实，但不修改业务代码、不删除失败测试、不启动 Subagent。

## 第 5 步：用 TDD 锁住回归

确认后使用 `/lx-tdd`，每个垂直切片遵循：

1. 先写能稳定复现原问题的外部行为测试（Red）；
2. 运行最小命令，确认失败来自已定位的 Bug；
3. 只写足够让回归测试通过的最小修复（Green）；
4. 运行同一测试和必要的相邻回归；
5. 如需重构，保持测试通过后再小步重构并重跑。

如果没有经济可行的自动化测试切面，必须记录原因，并用最小手工验收替代；不能用构建成功代替 Bug 回归验证。

## 第 6 步：按依赖执行 Subagent

需要拆给 Subagent 时使用 `/lx-subagent`，任务报告必须包含：

- 复现证据和根因是否已确认；
- 本任务修改范围和明确非目标；
- 回归测试与验证命令；
- 与其他任务的依赖、文件重叠和合并风险；
- 完成后仍未解决的风险。

默认串行。只有任务互不依赖、文件不重叠、验证命令独立且用户接受合并成本时才并行。

## 完成标准

Bug 修复只有在以下证据齐全时才可报告为完成：

- 原始复现路径已被回归测试或明确的手工验收覆盖；
- 根因对应的最小修复已通过验证；
- 相邻行为未出现新的回归；
- 修改范围、验证命令、未覆盖范围和剩余风险已报告；
- 未把超出本次范围的新需求混入修复。

最终不要只说“已修复”，要说明：复现是否先失败、改了什么、运行了什么、结果是什么。

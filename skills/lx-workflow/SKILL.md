# lx 工作流导航

你现在进入的是 `lx-cursor-workflow`。先向用户说明下面的阶段和产物，不要替用户跳过确认门：

## 规范优先级（强制）

在系统、平台安全规则和用户明确范围的边界内，公司/项目本地规范是最高工程约束。它们优先于本工作流、通用编码建议、`karpathy-guidelines`、`ponytail` 以及 CodeGraph 的推断。

公司/项目规范包括但不限于：

- 根目录和目标目录附近的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules` 等 Agent 规则；
- 项目指定的编码规范、领域约束、测试规范、接口/权限/安全约定；
- 页面、表单、列表、详情页和其他模板页面的创建规范；
- 公司或项目已有的公共组件、工具、脚手架、目录结构和依赖约定；
- `package.json` 脚本以及项目规定的 lint、类型检查、测试、构建、版本和发布流程；
- 项目已有的 `CONTEXT.md`、ADR 和其他明确记录的架构决策。

工作流只固化“规范优先级和冲突处理方法”，不把某一家公司的具体编码或页面规则写成所有项目的默认规则；具体要求必须来自当前目标项目。

开始分析或编码前：

1. 先按项目 `AGENTS.md` 指定的清单读取规范；没有清单时，只读取与本任务相关的本地规则和配置。
2. 创建页面或组件时，优先复用公司模板和公共组件；没有确认依据时，不自行发明另一套页面模板或公共抽象。
3. 把本次采用的规范来源和可能的冲突写进计划，确保实现和验证都能追溯。

### 冲突处理

- 公司/项目规范与 LX 流程冲突时：保留 LX 的需求澄清、Bug 复现、计划确认和验证目标，按公司规范调整具体实现、测试方式和交付步骤。
- `karpathy-guidelines` 或 `ponytail` 与公司编码、组件、模板、测试或安全要求冲突时：公司要求优先；它们只能在允许范围内帮助缩小改动、复用现有能力和减少重复代码。
- CodeGraph 只负责发现符号、调用关系和影响范围，不负责决定规范，也不能覆盖项目规则。
- 多份公司/项目文档互相冲突时，优先更具体、作用域更近且明确生效的规则；仍无法判断时，列出冲突和影响，停在计划阶段询问，不静默选择。
- 不修改公司规范来消除冲突，也不把通用工作流规则伪装成公司要求。

### 先分类

- 已有行为出错、回归、报错、性能退化或测试失败：先使用 `/lx-bugfix`，再按 `fast`、`standard`、`deep` 分级。
- 新增以前不存在的能力，或改变已确认的产品规则：使用 `/lx-grill`。
- 同时包含两类内容：拆成 Bug 修复线和新需求线，分别确认范围。

### 新需求线

1. `/lx-grill`：逐个问题澄清目标、边界、约束和验收标准。
2. `/lx-brainstorm`：基于已澄清的问题，产生多个候选方案并比较取舍。
3. `/lx-writing-plan`：把已选方案写成有依赖、切面和验收条件的计划。

### Bug 修复线

1. `/lx-bugfix`：固定复现事实、定位根因、定义回归测试切面和修复边界。
2. 先走 `fast` 门槛：单字段/单参数/单函数、入口明确、稳定断言、预计不超过 2 个文件时直接快速处理；接口边界本身不自动升级，契约未知或真实响应矛盾才升级。
3. 根因或修复方向不清晰时，再使用 `/lx-brainstorm` 比较方案；简单且根因已确认时跳过 Brainstorm 和 Subagent。
4. `/lx-writing-plan`：把“复现 → 回归测试 → 最小修复 → 验证”写成计划；快速模式使用轻量计划确认。

### 共同收口

1. 用户明确确认计划后，才使用 `/lx-tdd` 或 `/lx-subagent`。
2. 实施后运行项目已有验证命令，并让用户审阅 diff。

## 统一规则

- 文档按需写入项目的 `docs/lx-workflow/`。
- 先读取 `docs/lx-workflow/CONTEXT.md`（如果存在）和其中相关 ADR。
- 发现术语冲突时，先指出冲突并让用户选择，不要静默重命名。
- 没有明确的“确认计划”时，不修改业务代码、不创建测试、不启动 Subagent。
- 任何并行建议都必须说明任务依赖、文件重叠和合并风险。

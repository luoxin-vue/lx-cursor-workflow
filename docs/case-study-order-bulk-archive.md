# 员工花名册高级筛选与自定义表头：一眼看懂 lx 工作流

这是一个可以直接在 Cursor 中复现的完整使用案例。它以本次员工花名册迭代为业务背景，重点展示 `lx-*` Skills 如何把一句模糊的页面需求，变成有术语、有边界、有测试切面、可以交给 Subagent 执行的任务。

> 说明：下面的对话和命令是可复现的演示脚本，测试输出使用示例项目的典型结果表示。不同项目的目录、接口命名和测试命令会不同，但阶段顺序、确认门和产物结构不变。
>
> 本案例以本次员工花名册迭代中的“高级筛选 + 自定义表头”为主线，并把列表查询一致性作为实现阶段的约束：用户最终看到的列表必须是最后一次查询的结果，并且要与最新的筛选、表头偏好同帧出现。

## 需求起点：只有一句话

产品同事说：

> “员工花名册增加高级筛选和自定义表头能力。”

这句话至少隐藏了这些问题：

- 高级筛选字段是前端固定写死，还是由员工档案配置动态下发？
- “姓名”和“手机号”是两个条件，还是合并成一个“姓名/手机号”关键字？
- 筛选项放在页面顶部，还是从右侧抽屉打开？
- 用户调整筛选项顺序后，顶部常显区域显示哪几个字段？
- 关闭抽屉时，未点击查询的条件和拖拽顺序是否保留？
- 多选条件是字段内 OR、字段之间 AND，还是其他规则？
- 表头候选字段和高级筛选字段是否共用一份目录？
- “姓名”能不能隐藏或拖走？员工状态等系统必备字段能不能删除？
- 表头配置保存失败时，页面是否先应用本地改动？
- 用户快速连续查询或翻页时，旧响应是否可能覆盖新结果？
- 页面返回时，低频字段目录和高频选项是否都要重复请求？

如果直接让 Agent 写代码，它很可能会自行猜一个字段清单、一套参数名、一个本地存储结构和一套保存失败语义。

## 整体效果：输入、产物、代码边界

| 阶段 | 你输入什么 | Agent 产出什么 | 是否改业务代码 |
|---|---|---|---|
| `lx-grill` | 模糊需求和你的逐题回答 | 术语、边界、失败场景、验收标准 | 否 |
| `lx-brainstorm` | 已确认的问题和约束 | 3 个不同方案、取舍和推荐 | 否 |
| `lx-writing-plan` | 选定方案 | 任务、依赖、测试切面、验证命令 | 否 |
| 计划确认 | “确认计划，可以进入实现阶段” | `plan_status: approved` | 否 |
| `lx-tdd` | 一个垂直切片 | 失败测试 → 最小实现 → 通过证据 | 是 |
| `lx-subagent` | 已批准的任务清单 | 串行执行报告或安全的并行关系表 | 是 |

最重要的视觉效果是：前四行结束时，员工花名册业务代码仍然没有变化；确认门之后，才出现测试和实现 diff。

## 第 1 步：Grill 把“高级筛选”问具体

在 Cursor Agent 输入：

```text
/lx-grill 我想给员工花名册增加高级筛选和自定义表头能力
```

### 对话片段

Agent 一次只问一个问题，并给推荐答案：

```text
Agent：推荐把高级筛选字段改为独立配置驱动，而不是继续维护前端固定字段清单。
      这样员工档案新增可查询字段后，抽屉可以按配置自动渲染。
      第一个问题：高级筛选字段是否复用导出字段目录？

你：不复用。高级筛选和导出字段是两份独立目录，各自维护。

Agent：第二个问题：顶部筛选区和右侧抽屉的条件是否使用两套状态？

你：只使用一份条件模型。顶部常显字段取完整顺序的前 3 项，抽屉展示全部可查询字段。

Agent：第三个问题：用户调整筛选项顺序后，哪些字段进入顶部常显区域？

你：全部字段都可以排序，前 3 项进入顶部区域；顺序按账号保存，首次仍保持姓名/手机号、入职时间段、组织。

Agent：第四个问题：用户关闭抽屉时，未点击查询的条件和拖拽顺序如何处理？

你：关闭直接丢弃本次未提交改动；点击查询才应用条件、保存顺序并关闭抽屉；重置则清空条件并重新查询空列表。

Agent：第五个问题：表头自定义和高级筛选是否使用同一套字段目录？

你：不使用同一套目录。表头候选字段和高级筛选可查询字段独立维护。

Agent：第六个问题：表头中的固定字段和系统必备字段如何处理？

你：姓名固定第一列且不可隐藏；系统必备字段不可隐藏、不可删除，但允许调整顺序；操作列始终固定在右侧。

Agent：第七个问题：查询和保存失败时，页面采用什么一致性规则？

你：只应用最后一次查询的响应；偏好保存成功后才应用新状态，失败则回滚并提示；本地存储只作为读取兜底。
```

### Grill 结束时的产物

Agent 不写代码，而是总结成一组可以复用的决策：

```text
目标：员工花名册支持由配置驱动的高级筛选和按账号保存的自定义表头。

高级筛选边界：
- 筛选字段由独立的“可查询字段配置”驱动，不复用导出字段目录。
- “姓名/手机号”是合并关键字字段；组织、岗位、职级等字段保持联动。
- 抽屉展示全部可查询字段；所有字段均可排序，顶部区域取顺序前 3 项。
- 顶部区域和抽屉共用一份条件模型，非空条件取交集。
- 关闭抽屉丢弃未提交改动；查询才应用条件；重置清空条件并重新查询。
- 查询结果行显示“筛选出 xx 人”和已应用条件标签；标签纯展示、不可单独关闭。

表头边界：
- 表头候选字段目录与高级筛选字段目录独立维护。
- 姓名固定第一列、不可隐藏、不可拖动。
- 系统必备字段不可隐藏或删除，但可以拖动换位置。
- 操作列恒固定在右侧，不参与表头配置。
- 关闭设置弹窗丢弃未保存改动，点击确定才保存并应用。

一致性与请求边界：
- 列表查询使用查询序号守卫，旧响应不得覆盖新响应。
- 字段目录、筛选顺序、表头目录和表头顺序未就绪时，查询参数和列表结果都要经过偏好闸门。
- 组织树、字典、合同类型等稳定选项集不随每次列表查询重复加载。
- 表头或筛选排序保存失败时，保持旧状态，不用失败结果触发重查。

验收方向：
- 配置新增可查询字段后，抽屉能自动出现对应筛选项。
- 单选、多选、日期区间和组织条件能正确映射为列表查询参数。
- 快速查询、翻页和首次打开立即查询时，最终结果和条件都不丢失。
- 表头显隐、排序、锁定规则和保存失败回滚符合约定。
```

此时可以让同事看项目目录：没有新增接口、测试或业务文件，只有需求术语、数据边界和验收方向被说清楚了。

## 第 2 步：Brainstorm 不急着选第一个方案

输入：

```text
/lx-brainstorm
```

Agent 根据刚才的约束给出三个真正不同的方向：

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| A：继续维护固定字段 | 保留页面内固定筛选项和硬编码表头，只增加一个抽屉外观 | 改动小、上线快 | 新增档案字段仍要改前端；无法真正覆盖全部可查询字段；表头个性化能力有限 |
| B：独立目录 + 通用条件 + 独立表头偏好 | 高级筛选由独立配置驱动，配置项走 `configFilters`；表头通过字段目录和列偏好控制 | 与字段配置解耦，能覆盖动态字段；固定字段和自定义字段边界清晰；最适合长期维护 | 需要明确两份目录、查询参数和保存失败语义；前端状态编排更复杂 |
| C：复用导出字段目录 | 用导出字段目录同时驱动高级筛选和表头候选字段 | 少一套目录，初期接口数量少 | “姓名/手机号”合并、日期区间、控件类型和导出语义不一致；后续会被两种业务互相牵制 |

推荐方案是 B：独立字段目录、通用条件查询和独立表头偏好。

理由是员工花名册的筛选和导出虽然都来自员工档案，但它们解决的是不同问题：筛选需要控件类型、条件模型和联动关系，导出需要导出字段和文件列结构；表头又有“姓名锁第一列、系统必备字段不可隐藏”的展示约束。强行复用目录只会把当前的代码量减少，增加后续契约和维护成本。

在该方案下，列表查询的配置项条件可以统一组装为：

```text
POST /api/ftb/web/personnels-staff-roster/query-list/pageList

body = {
  固定筛选项,
  configFilters: [
    { fieldId: 'eduBackground', values: ['3'] },
    { fieldId: 'entryDate', start: '2026-01-01', end: '2026-03-31' }
  ],
  currentPage,
  pageSize
}
```

用户确认：

```text
选 B。高级筛选、表头候选字段和导出目录各自维护；列表查询使用固定项 + configFilters。
表头保存和筛选排序保存都采用后端优先，成功才应用，失败保持原状态并提示。
```

此时仍然没有写代码。

## 第 3 步：Writing Plan 把方案拆成垂直任务

输入：

```text
/lx-writing-plan
```

Agent 在项目中创建类似下面的计划：

```yaml
plan_status: awaiting-user-confirmation
```

```markdown
# 员工花名册高级筛选与自定义表头

## 已确认方案

高级筛选使用独立字段配置，页面将固定筛选项与 `configFilters` 合并提交到
`query-list/pageList`；抽屉和顶部区域共用一份条件模型，前 3 项根据账号保存的完整顺序展示。

表头使用独立的字段目录和列偏好：姓名固定第一列，系统必备字段不可隐藏，操作列固定右侧。
两类偏好都遵循“保存成功才应用，失败保持旧状态”的语义。

## 任务

1. 固化员工花名册的字段术语和数据契约
   - 测试切面：筛选字段归一化、固定字段与配置字段的分类
   - 验收：姓名/手机号、日期区间、组织、岗位、职级及配置字段的 key 和控件类型明确

2. 实现高级筛选条件模型与查询参数组装
   - 阻塞：任务 1
   - 测试切面：`buildConfigFilters` / `buildQueryParams`
   - 验收：只提交非空条件；单选、多选、日期区间正确映射；字段内 OR、字段间 AND 的契约不被前端破坏

3. 实现高级筛选顺序、顶部前 3 项和条件标签
   - 阻塞：任务 1、2
   - 测试切面：`loadFilterOrder` / `saveFilterOrder`、条件标签纯函数
   - 验收：首次顺序保持现状；按账号保存；关闭丢弃草稿；查询后徽标和标签数量一致

4. 实现表头字段目录、候选池和列偏好
   - 阻塞：任务 1
   - 测试切面：`columnConfigUtil` 的字段分类、显隐迁移、去重和持久化
   - 验收：姓名锁第一；系统必备字段不可隐藏；选择更多字段幂等；操作列不进入配置

5. 接入列表查询一致性编排
   - 阻塞：任务 2、3、4
   - 测试切面：查询序号守卫、偏好闸门、保存失败回滚和稳定选项集加载
   - 验收：旧响应不覆盖新响应；带条件查询不丢 configFilters；表头和数据同帧出现；保存失败不应用新列集

6. 运行相关 fast 场景、接口联调和页面手工验收
   - 阻塞：任务 1-5
   - 验收：覆盖高级筛选、表头设置、列表查询和保存失败的最小行为；记录未覆盖的渲染与真实时序风险
```

计划中有三处值得现场放大：

1. 高级筛选和表头虽然都发生在员工花名册，但它们使用两份独立字段目录，避免把两个概念揉成一个万能配置。
2. 每个任务都有最高公共测试切面：优先测条件、状态迁移和请求组装，不把测试绑死在拖拽或渲染细节上。
3. `awaiting-user-confirmation` 明确表示 Agent 现在不能修改花名册业务代码。

## 第 4 步：计划确认门

用户审阅计划后输入：

```text
我确认这个计划，可以进入实现阶段。按任务顺序执行，先完成高级筛选条件模型切片。
```

Agent 才能把状态更新为：

```yaml
plan_status: approved
```

如果用户说“差不多，先把抽屉写出来看看”，仍然不应视为确认；这正是确认门要防止的模糊授权。因为抽屉长什么样并不能决定字段契约、保存语义和列表查询是否正确。

## 第 5 步：TDD 从一个行为开始

输入：

```text
/lx-tdd
```

Agent 读取批准计划，先选任务 2 的最小行为：一个配置驱动的单选筛选条件，应被转换为 `configFilters` 中的一条公共条件。

### Red：先写一个外部行为测试

示例测试形态：

```ts
it('builds a config filter for a selected employee field', () => {
  const result = buildConfigFilters(
    [{ key: 'eduBackground', type: 'select' }],
    { eduBackground: ['3'] },
  )

  expect(result).toEqual([
    { fieldId: 'eduBackground', values: ['3'] },
  ])
})
```

运行项目已有命令，得到失败证据（示例）：

```text
FAIL  buildConfigFilters › builds a config filter for a selected employee field
Error: buildConfigFilters is not implemented
```

### Green：只写够用的实现

Agent 只实现让这个行为通过的最小路径，然后重新运行同一个测试：

```text
PASS  buildConfigFilters › builds a config filter for a selected employee field
Tests: 1 passed, 1 total
```

### 下一轮切片

接着增加第二个行为：日期区间只生成一条包含 `start` / `end` 的条件，不再把区间起止拆分键重复发送；再增加第三个行为：字段目录加入新可查询字段后，条件组装无需新增前端分支。

表头切片可以单独验证另一条公共缝：

```text
保存成功 → 更新本地兜底 → 应用新 columnState → 重查列表
保存失败 → 保持旧 columnState → 不重查列表 → 提示错误
```

查询一致性再验证两条边界：旧查询响应晚于新查询响应时丢弃旧响应；偏好未就绪时，带条件查询要等字段目录就绪后再构建 `configFilters`。

每一轮都重复：

```text
一个行为 → 一个失败测试 → 最小实现 → 通过证据
```

这时现场可以强调：TDD 不是先写一大批 UI 测试，而是让每个数据契约、状态迁移和请求编排决定都被下一条反馈约束。

## 第 6 步：Subagent 按任务执行

输入：

```text
/lx-subagent
```

Agent 先给出任务关系，而不是立刻开多个并行上下文：

```text
任务 1：字段术语与数据契约                  → 串行起点
任务 2：高级筛选条件模型与 configFilters      → 依赖任务 1
任务 3：筛选顺序、顶部前 3 项和条件标签        → 依赖任务 1、2
任务 4：表头目录、候选池和列偏好               → 依赖任务 1，可与任务 2 并行
任务 5：查询序号守卫、偏好闸门和保存回滚       → 依赖任务 2、3、4
任务 6：fast 场景、接口联调和手工验收          → 依赖任务 5
```

默认执行顺序是 1 → 2 → 3 → 4 → 5 → 6。任务 2 和任务 4 理论上可以并行，但它们是否真正适合并行，要看是否修改同一个花名册入口文件、是否共享同一份状态和验证命令；不能只因为“前后端看起来是两块”就并行。

每个 Subagent 返回：

- 完成了哪个任务；
- 修改了哪些文件；
- 运行了哪些测试和结果；
- 是否遇到超出任务范围的问题；
- 下一个任务的前置条件是否满足。

它不能自行批准计划、扩大需求、把高级筛选目录和表头目录合并、删除失败测试或自动提交推送。

## 这个案例改变了什么

### 之前

```text
一句“员工花名册增加高级筛选和自定义表头”
→ Agent 自行猜字段目录、查询参数、列规则和保存语义
→ 代码写完后才发现筛选目录、导出目录和表头目录被混成一套
→ 快速查询或保存失败时，页面出现旧数据覆盖、新列全空等问题
```

### 之后

```text
逐题澄清业务术语
→ 独立字段目录与通用条件方案比较
→ 带测试切面的任务计划
→ 用户确认
→ 一个行为一个 TDD 回路
→ 查询守卫、偏好闸门和保存回滚统一约束
→ Subagent 在明确边界内执行
```

真正的收益不是多了几个命令，而是每个阶段都有“看得见的中间产物”：

- 高级筛选的“可查询字段”不再和导出字段、表头候选字段混为一谈；
- 条件模型和列表接口之间有明确映射；
- 表头的固定字段、系统必备字段和操作列有明确边界；
- 竞态、空表帧和保存失败等问题在实现前就进入验收清单；
- 发生后端契约变化时，可以定位影响的是筛选、表头还是列表响应，而不是重新猜整页逻辑。

## 现场演示建议

如果只有 10 分钟，按这个顺序展示：

1. 先贴出开头那句模糊需求。
2. 展示 `lx-grill` 的三个追问：独立字段目录、共用条件模型、保存失败语义。
3. 快速展示三个方案和为什么不复用导出字段目录。
4. 打开计划文件，放大 `plan_status: awaiting-user-confirmation`。
5. 输入确认语句，再展示一个 `buildConfigFilters` 的 Red → Green 切片。
6. 最后展示查询序号守卫、偏好闸门和 Subagent 任务关系，解释为什么不是所有任务都应该并行。

一句话收尾：

> “把 Agent 的自由度放在方案空间里，把代码阶段的自由度放在已经确认的字段、状态和任务边界里。”

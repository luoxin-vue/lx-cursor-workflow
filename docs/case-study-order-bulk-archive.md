# 订单批量归档：一眼看懂 lx 工作流

这是一个可以直接在 Cursor 中复现的完整使用案例。它用一个常见但不简单的需求，展示 `lx-*` Skills 如何把一句模糊想法变成有测试切面、有依赖关系、可以交给 Subagent 执行的任务。

> 说明：下面的对话和命令是可复现的演示脚本，测试输出用示例项目的典型结果表示。不同项目的目录、测试命令和接口命名会不同，但阶段顺序、确认门和产物结构不变。

## 需求起点：只有一句话

产品同事说：

> “订单列表增加一个批量归档能力。”

这句话至少隐藏了这些问题：

- 什么状态的订单可以归档？
- 批量操作是同步完成，还是提交后台任务？
- 一次最多多少条？能不能跨页选择？
- 部分订单失败时，成功的订单要不要保留？
- 谁可以操作？操作是否需要审计记录？
- 归档后还能不能恢复？列表默认是否隐藏归档订单？

如果直接让 Agent 写代码，它很可能会自行猜一个 API、一个按钮和一个数据库更新方式。

## 整体效果：输入、产物、代码边界

| 阶段 | 你输入什么 | Agent 产出什么 | 是否改业务代码 |
|---|---|---|---|
| `lx-grill` | 模糊需求和你的逐题回答 | 术语、边界、失败场景、验收标准 | 否 |
| `lx-brainstorm` | 已确认的问题和约束 | 3 个不同方案、取舍和推荐 | 否 |
| `lx-writing-plan` | 选定方案 | 任务、依赖、测试切面、验证命令 | 否 |
| 计划确认 | “确认计划，可以进入实现阶段” | `plan_status: approved` | 否 |
| `lx-tdd` | 一个垂直切片 | 失败测试 → 最小实现 → 通过证据 | 是 |
| `lx-subagent` | 已批准的任务清单 | 串行执行报告或安全的并行关系表 | 是 |

最重要的视觉效果是：前四行结束时，业务代码仍然没有变化；确认门之后，才出现测试和实现 diff。

## 第 1 步：Grill 把“批量”问具体

在 Cursor Agent 输入：

```text
/lx-grill 我想给订单列表增加批量归档能力
```

### 对话片段

Agent 一次只问一个问题，并给推荐答案：

```text
Agent：推荐先限定为“已完成订单”，因为未完成订单归档可能绕过退款和履约流程。
      第一个问题：哪些订单状态允许被批量归档？

你：只允许已完成订单。

Agent：第二个问题：用户选择跨页订单时，系统按“当前页选中”还是“筛选结果全部选中”处理？

你：只处理当前页面明确勾选的订单，避免用户误操作大量数据。

Agent：第三个问题：一次最多允许提交多少条？

你：最多 100 条，超过就阻止提交并提示用户分批处理。

Agent：第四个问题：部分订单失败时，已经成功归档的订单是否保留？

你：保留成功结果，并返回每条订单的成功或失败原因。

Agent：第五个问题：归档操作是否需要权限和审计？

你：需要 `order:archive` 权限；记录操作人、订单 ID、时间和结果。
```

### Grill 结束时的产物

Agent 不写代码，而是总结成一组可以复用的决策：

```text
目标：订单列表支持对当前页明确勾选的已完成订单进行批量归档。

边界：
- 仅允许已完成订单；未完成订单必须逐条返回不可归档原因。
- 单次最多 100 条；超过上限在提交前阻止。
- 只处理当前页明确勾选的订单，不处理“筛选结果全选”。
- 部分成功允许保留，结果必须逐条可见。

权限与审计：
- 调用者必须拥有 order:archive 权限。
- 每条结果记录操作人、订单 ID、时间和结果。

验收方向：
- 全部成功时，列表刷新并显示成功数量。
- 混合结果时，用户能看到成功和失败的订单及原因。
- 无权限、超上限、状态不允许时，不产生未授权的归档结果。
```

此时可以让同事看项目目录：没有新增接口、测试或业务文件，只有约定被说清楚了。

## 第 2 步：Brainstorm 不急着选第一个方案

输入：

```text
/lx-brainstorm
```

Agent 根据刚才的约束给出三个真正不同的方向：

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| A：前端循环单条归档 | 前端逐条调用已有单条归档接口 | 复用现有能力，后端改动小 | 请求多、部分失败处理分散、审计顺序不稳定 |
| B：同步批量接口 | 新增 `POST /orders/archive-batch`，一次返回逐条结果 | 结果明确、权限和审计集中、最适合 100 条上限 | 需要新增接口和事务边界 |
| C：异步批量任务 | 提交任务，后台处理，前端轮询进度 | 大批量扩展性好 | 当前上限只有 100 条，任务状态和 UI 成本过高 |

推荐方案是 B：同步批量接口。理由是当前规模有明确上限，用户需要立即看到逐条结果，异步任务暂时是过度设计。

用户确认：

```text
选 B。接口同步返回逐条结果，成功和失败分别保留；先不做异步任务。
```

此时仍然没有写代码。

## 第 3 步：Writing Plan 把方案拆成垂直任务

输入：

```text
/lx-writing-plan
```

Agent 在项目中创建类似下面的计划：

```yaml
plan_status: awaiting-user-confirmation
```

```markdown
# 订单批量归档

## 已确认方案

新增同步批量归档接口。接口接受当前页面勾选的订单 ID，逐条校验权限、状态和幂等条件，并返回逐条结果；前端展示成功数、失败数和失败原因。

## 任务

1. 定义批量归档请求和逐条结果的公共接口
   - 测试切面：批量归档服务的公共调用接口
   - 验收：100 条以内可表达逐条成功/失败；超过 100 条被拒绝

2. 实现已完成状态校验和幂等行为
   - 阻塞：任务 1
   - 测试切面：批量归档服务
   - 验收：未完成订单失败；已归档订单不会重复产生新的归档结果

3. 实现权限校验和逐条审计结果
   - 阻塞：任务 1
   - 测试切面：批量归档服务
   - 验收：无 order:archive 权限时拒绝；每条结果携带可审计信息

4. 接入订单列表的当前页勾选状态
   - 阻塞：任务 1、2、3
   - 测试切面：订单列表用户操作
   - 验收：只提交明确勾选的订单；提交后展示成功和失败数量

5. 运行项目已有测试、类型检查和前端验证命令
   - 阻塞：任务 1-4
```

计划中有三处值得现场放大：

1. 每个任务是一个可观察的垂直切片，而不是“先把前端、后端、测试全部写完”。
2. 每个任务都写了最高公共测试切面。
3. `awaiting-user-confirmation` 明确表示 Agent 现在不能改业务代码。

## 第 4 步：计划确认门

用户审阅计划后输入：

```text
我确认这个计划，可以进入实现阶段。按任务顺序执行，先完成服务层切片。
```

Agent 才能把状态更新为：

```yaml
plan_status: approved
```

如果用户说“差不多，先写起来看看”，仍然不应视为确认；这正是确认门要防止的模糊授权。

## 第 5 步：TDD 从一个行为开始

输入：

```text
/lx-tdd
```

Agent 读取批准计划，先选任务 1 的最小行为：全部订单都是已完成且有权限时，返回逐条成功结果。

### Red：先写一个外部行为测试

示例测试形态：

```ts
it('returns one successful result for each completed order', async () => {
  const result = await archiveOrders({
    orderIds: ['order-101', 'order-102'],
    actor: operatorWith('order:archive'),
  });

  expect(result).toEqual({
    succeeded: ['order-101', 'order-102'],
    failed: [],
  });
});
```

运行项目已有命令，得到失败证据（示例）：

```text
FAIL  archiveOrders › returns one successful result for each completed order
Error: archiveOrders is not implemented
```

### Green：只写够用的实现

Agent 只实现让这个行为通过的最小路径，然后重新运行同一个测试：

```text
PASS  archiveOrders › returns one successful result for each completed order
Tests: 1 passed, 1 total
```

### 下一轮切片

接着才增加第二个行为：混合状态时逐条返回失败原因。每一轮都重复：

```text
一个行为 → 一个失败测试 → 最小实现 → 通过证据
```

这时现场可以强调：TDD 不是“先写一大批测试”，而是让每个实现决定都被下一条反馈约束。

## 第 6 步：Subagent 按任务执行

输入：

```text
/lx-subagent
```

Agent 先给出任务关系，而不是立刻开多个并行上下文：

```text
任务 1：请求/结果接口与服务入口       → 串行起点
任务 2：状态校验与幂等                 → 依赖任务 1
任务 3：权限与审计                     → 依赖任务 1，可与任务 2 并行
任务 4：列表勾选与结果展示             → 依赖任务 1、2、3
任务 5：全量验证                       → 依赖任务 4
```

默认执行顺序是 1 → 2 → 3 → 4 → 5。虽然任务 2 和任务 3 理论上可并行，但只有在文件不重叠、验证命令独立且用户接受合并成本时，才建议并行。

每个 Subagent 返回：

- 完成了哪个任务；
- 修改了哪些文件；
- 运行了哪些测试和结果；
- 是否遇到超出任务范围的问题；
- 下一个任务的前置条件是否满足。

它不能自行批准计划、扩大需求、删除失败测试或自动提交推送。

## 这个案例改变了什么

### 之前

```text
一句“增加批量归档”
→ Agent 自行猜 API、权限、失败处理和测试方式
→ 代码写完后才发现产品理解不同
```

### 之后

```text
逐题澄清
→ 多方案比较
→ 带测试切面的任务计划
→ 用户确认
→ 一个行为一个 TDD 回路
→ Subagent 在明确边界内执行
```

真正的收益不是多了几个命令，而是每个阶段都有“看得见的中间产物”，错误假设会在变成代码之前暴露。

## 现场演示建议

如果只有 10 分钟，按这个顺序展示：

1. 先贴出开头那句模糊需求。
2. 展示 `lx-grill` 的两个追问，让大家看到需求如何变具体。
3. 快速展示三个方案和推荐理由。
4. 打开计划文件，放大 `plan_status: awaiting-user-confirmation`。
5. 输入确认语句，再展示一个 Red → Green 切片。
6. 最后用任务关系表解释为什么不是所有 Subagent 都应该并行。

一句话收尾：

> “把 Agent 的自由度放在方案空间里，把代码阶段的自由度放在已经确认的任务边界里。”
